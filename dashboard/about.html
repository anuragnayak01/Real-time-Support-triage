About InsightPulse
How the triaging pipeline is built, and why
Project overview
A real-time support ticket triager built on an agentic retrieval pipeline.
Incoming messages are embedded, classified against a 14-category taxonomy, scored for priority and sentiment, and persisted — all before the ticket ever reaches a human queue. This page walks through the stack and the flow one message takes end to end.

Message pipeline
1
Ingest
A message arrives from the demo form, an email hook, or another channel, tagged with its source (email, chat, phone, social).
2
Orchestrate
A LangGraph graph routes the message through the triage flow, coordinating retrieval, classification, and scoring steps as graph nodes.
3
Retrieve context
The message is embedded with BGE-small-en-v1.5 and matched against similar historical tickets in ChromaDB via LlamaIndex, giving the classifier real precedent to work from.
4
Classify & score
CrewAI agents assign one of 14 issue-type categories, a priority (Critical / High / Low), and a sentiment label + score, returned as structured output from Groq.
5
Persist & serve
The result is written to SQLite and served through FastAPI, which this dashboard polls to render tickets, charts, and the live demo.
Tech stack
LangGraphOrchestrates the triage flow as a graph
CrewAIClassification agents for taxonomy + priority
LlamaIndexRetrieval layer over historical tickets
ChromaDBVector store for embedded tickets
BGE-small-en-v1.5Sentence embeddings for retrieval
GroqLow-latency structured-output inference

Vercel + RenderFrontend and backend deployment
Deployment notes
The dashboard is static HTML/CSS/JS served from Vercel; a vercel.json proxy forwards /tickets/* and /triage to the FastAPI backend on Render, avoiding CORS issues between the two origins. Ticket data is cached client-side for 20 seconds per tab so navigating between Overview, Tickets, and Analytics doesn't refetch unnecessarily.
